The three you asked me to explain

G-13 · Hooks live in the repo

A hook is a small command the coding agent runs at set points: before it edits a file, after it runs a command, before it commits. PairedDev lets a project define them, and a tenant admin define ones that projects must not remove (for example “never edit .github/workflows”). The agent runs on a GitHub runner and reads its hooks from a file committed in the repository (.claude/settings.json for Claude Code), not from our database.

The board can write that file, and checks hooks on commits made through the Work tab. But anyone who can push to the repo can edit the file, so the “tenant-admin hooks cannot be weakened by a project” rule cannot be enforced in the repo. We can only detect it: on every sync the board compares the file to what it expects, records an audit_event and shows a banner if it differs. Branch protection with required review on that path makes it hard to change without a second person.

New with Muse Code. The file name and format are agent-specific. Before building hooks we need to check where Muse Code reads its hooks and whether it supports them. If it does not, hooks become advisory for that agent and the board's own checks (Work-tab commits, plan gates) are the real control. to verify

G-07 · Metrics history

Resolved: not a gap. Each tenant is its own company with its own board, so its charts start when that tenant starts and fill in as it works. Nothing is shared between tenants, and no history is expected before a tenant's first day. The only requirement is that we keep recording moves from the start, because a card row alone only shows where it is now: a lane_transition row on every move and a nightly flow_snapshot of counts per lane. A Glyph computes the charts from those rows, always inside one tenant.

The prototype's 90-day series is mock data. The empty-state copy on the charts should say “Charts fill in as your team works”, and a demo tenant can be filled by pd_seed_demo.

G-20 · AWS connector

Resolved. The AWS connector creates the hosting stack once, when a brand new project is created: an S3 bucket, CloudFront, certificate, DNS and an OIDC role for GitHub (for PairedDev itself, paireddev.com). After that, every merge of agent work deploys through workflows, not the connector: the coding agent writes GitHub Actions workflows into the repo, and those build the static export, sync it to S3, and invalidate CloudFront, signing in to AWS through the OIDC role (the connector can look up the OIDC provider). The agent's own setup (setup_workflow, setup_permissions, setup_secret) is separate and runs once per repo. Nothing in the connector needs an update.

High severity

G-01 · Live Session: no step stream, no mid-session approval

Requirement. Sessions stream step by step (read, edit, test, PR). A hook set to ask halts the session until a human approves or denies inline. “A poll-and-replace implementation will read wrong.”

Platform. The Claude Code connector is two actions, start_task and get_task, plus one-time repo setup. It triggers a GitHub Actions workflow on a runner; the board learns about it through get_task state and GitHub webhooks (push, pull_request, check_suite, workflow_run). There is no per-tool-call stream and a headless runner cannot wait for a person. The WebSocket gateway does stream every turn of a nostackai Crew, and crews have a real tool-approval pause with POST /agents/decision.

  • A · Runner only. Session panel shows phases (queued, running, commit pushed, PR opened, checks). Protected-path rules become plan-time approval: the plan lists them and approving the plan approves them; other hooks are block.
  • B · Crew developer agent. A nostackai crew edits files through GitHub connector calls (via a Glyph tool). Full per-turn stream and inline approval, exactly the design. It is a nostackai agent on an Anthropic model, not Claude Code, so it has no local test runner or shell.
  • C · Hybrid. Plan by crew, code by runner (A) in v1; add B behind the live-session flag later.

Recommendation. C. It delivers requirements 2, 4 and 5 fully and requirement 3 partially. Decision needed: is step-level fidelity a launch requirement?

G-02 · Plan and limits unknown

Observed. get_usage failed with a 403 (“Authorization header requires Credential…”), so I cannot see the org's plan. The same call fails the same way on a different org's key, so this is a bug in the MCP tool, not a property of this org. Read the plan in the console.

Why it matters. Schedules are paid only (Starter: 10 per tenant, 15-minute minimum; Pro: 100, 1-minute). Free allows 10 feature flags and we propose 12. Free allows 10 Glyph runs a day and 250 a month; Starter 200 and 5,000. A nightly snapshot per tenant plus metrics calls would exhaust Free almost immediately. Large Glyphs are Pro only.

Options. Confirm the plan in the console; or trim to 10 flags and drop schedules (sessions then rely on webhooks only; no flow history). Recommendation. Pro for the build; the flag list is cheap to trim.

G-06 · Backlog: totals, search, numbered pages

Requirement. “1 – 50 of 127 items”, “page 2 of 3”, text search, 7 combinable filters, built for hundreds of items, one server-side query.

Platform. Lists use a continuation token (cursor), not offsets. A list can stop after about 2,000 scanned records. Counts are a separate route with a capped flag. list_entities has attribute filters (contains, begins, comparisons) but no full-text search and no “total matching” beside a page, unless the instance has the Enterprise search add-on (OpenSearch), which adds ?q= search, totalcount and facets. Without it those return an empty result with a note.

Plan. pd_dev_list_items uses indexed lookups for project and lane, attribute filters for the rest, walks cursors to build the requested page, and returns total plus capped. Exact up to ~2,000 matching rows; beyond that the UI shows “2,000+” and Prev/Next. Tags are stored as one searchable string.

Decision. Is that acceptable? Larger tenants would need a different search backend, which nostackai does not offer through MCP.

G-13 · Hooks live in the repo

Requirement. Hooks configured per project; org-managed hooks cannot be widened by a project; commit_files is checked against hooks.

Platform. Hooks for Claude Code are .claude/settings.json in the repository, run by the runner. The connector's setup_workflow only commits the GitHub Actions workflow file (and leaves an existing copy alone); it does not write the hooks file, so the board writes that itself. The board can render the file from hook rows and commit it (commit_files), and can check hooks for commits made through the Work tab, but it cannot stop someone with repo write access editing the file.

Mitigations. Render tenant-admin hooks first and team hooks after; compare the repo copy on every sync and write an audit_event plus a banner on drift; use set_branch_protection with required review on .claude/**. Recommendation. Accept this; a repo-level lock is outside the platform's control.

Medium severity

G-03 · Write-only provider keys from inside the app

Requirement. The org connects Anthropic or Google from a credential modal; the key is write-only.

Platform. No MCP tool sets keys. Tenant admins enter them in the console (Tenant Settings → AI). An app-side route /app/paired-egih/tenant/settings exists for tenant-admin tokens, but I have not verified that the AI-key group is writable through it. Plan. v1 shows provider status (connected / not) and a deep link to the console; test the app-side route once the org is built and move the modal over only if it works.

G-04 · Tenant creation is console-only

MCP can list tenants (list_org_tenants → 2vrdf) but not create one. The app itself creates a tenant when a new admin signs up without a tenant id in a multi-tenant org (see the decision above), so no console step is needed per tenant, only pd_adm_bootstrap_tenant after sign-up. Connector secrets, AI keys, webhook secrets and SSO are still console-only. The runbook is in the build plan.

G-05 · Bedrock / Vertex / Foundry

Requirement 7 and section 13 offer Anthropic routed through a cloud gateway. The AI provider catalogue has protocol-level entries (anthropic, openai, gemini) and custom providers with a base URL (the case study uses one for Kimi). Bedrock needs AWS request signing and Vertex needs Google OAuth, neither of which a key-plus-base-URL provider can do. Foundry may work if it speaks the Anthropic protocol with a key; untested. Plan. Ship without gateways; keep the bedrock-routing flag off; ask the platform team.

G-07 · Metrics history

Cumulative flow, cycle time, throughput and burndown need per-day history, and item rows only hold current state. We record lane_transition on every move and a nightly flow_snapshot, and compute everything in a Glyph, per tenant. Each tenant is a separate company and board, so its charts simply start on its first day. Closed. A small Glyph has a 30-second ceiling, so very large ranges may need the Pro large Glyph.

G-11 · Ids like ITR-118

Record ids are generated by the platform and cannot be supplied. Each entity can have an autoincrement column; with a formula column the readable key is {project_key}-{number}. To check on first build: the counter is per tenant, and it is shared across projects in a tenant. Fallback: a counter on project incremented inside the create block.

G-12 · Portal without sign-in

The requirements call the portal public. nostackai supports no-login create and read on /app/{org}/public/{entity}, but a no-login request carries no token, so there is no tenant to resolve, and reading needs a restricted projection and an exact-match index. Voting and “My submissions” need identity anyway. Recommendation. Requesters sign in (invite or allowed email domain per tenant), landing on the least-privileged pd-requester policy.

G-14 · Dev tier only

Every MCP session is dev-tier. Promotion needs a paid plan, a provisioned Production environment, and a console deploy (publish → activate, with rollback). Feature-flag definitions and all assets are created in dev and reach production the same way; only the on/off switch works in prod directly. Allowed Domains and App URL are separate per environment.

G-16 · Admin policy bypass

The built-in adminacl is wildcard on wildcard, so a tenant admin can write governed tables directly, skipping the gate blocks. Options: accept (admins are trusted; the platform's own audit still records it), or give admins pd-admin instead, which breaks nothing in PairedDev but may limit console tenant-management actions. Recommendation. Accept, never assign adminacl to an agent, document it.

G-18 · Board as MCP tools

The requirements say the same operations “should exist as MCP tools so Claude Code can drive the board”. The nostackai MCP is design-time only and cannot read or write records. Claude Code would instead call the tenant's REST / Logic Block routes with an agent service token (the pd-agent policy). Plan. Ship a small repo skill describing those calls; a bespoke MCP server wrapping them is a separate project.

G-21 · Tenancy mode

Org tenancy is single, hybrid or multi, and moving up is a one-way door. get_org_info does not show the mode; one tenant exists. Confirm in Org Settings that it is multi before promising multiple customers.

Channels are not private inside a tenant, so names are unguessable and blocks authorise. The front-end wraps this behind the same adapter shape the skills call for.

Known and recorded in the requirements. Personal and shared fine-grained PATs work today.

G-10 · Crew tools

Tool entries are fixed at config time, so a crew that needs five repo actions has five tool entries.
