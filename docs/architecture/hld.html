High-level design

How PairedDev works on nostackai

A static front-end talks to one nostackai org (paired-egih) over its app API. Everything the backend does — data, rules, agents, git — is an Entity, Logic Block, Glyph, Crew, Event, Schedule or Connector defined through MCP. No nostackai source is touched.

Terminology trap. The requirements say “org” for a customer company (org-managed hooks, org providers). In nostackai that is a tenant. The nostackai org (paired-egih) is PairedDev the product. This pack always says tenant for a customer company and nostackai org for the vendor. “Org-managed hooks” become tenant-admin-managed hooks.

1 · System context

Three kinds of actor, one backend. Agents are never given board-wide tokens: Muse Code runs on a GitHub runner and reports back through GitHub webhooks and the connector, and every state change is made by a Logic Block that checks who is asking.

3 · Multi-tenancy

One nostackai org serves many customer tenants. The tenant is derived from the signed-in user's token, so no screen, block or query ever passes a tenant id. The same Entities, Logic Blocks and Crews exist for every tenant; the data, credentials, AI keys, GitHub tokens, hooks and flag overrides are the tenant's own.

  • Onboarding a tenant is partly console-only: nostackai has no MCP tool to create a tenant. See gap G-04 and the onboarding runbook in the build plan.
  • Per-tenant vs shared values. Anything that differs per tenant (repo owner, Slack channel, GitHub token, provider key) is read through {{params.settings.KEY}} or a connector, never written into a block (valueScopeGuide).
  • Anonymous access. The portal needs a signed-in requester. A no-login route cannot know which tenant it serves. See G-12.

4 · Card lifecycle and the three gates

Seven lanes. Lane changes are not column drags against the table; they are calls to move-item or advance-item, which return 409 when a gate is closed.

6 · Enforcing “agents never sign off or merge”

This is requirement 4 and it has to hold on the server. nostackai ACL only sees the route name, never the request body, so the rule is built from three layers rather than one.

  • Layer 1 works because each restricted operation is its own Logic Block, so it has its own action name a policy can deny.
  • Governed entities (work_item, checklist_item, audit_event, plan, agent_session) have direct create/update/delete denied for every role. Blocks are the only route in, which is the board-policy pattern from the case study.
  • audit_event is created with no update or delete grant in ACL (the platform has no excludeOps option), so append-only is enforced by access control rather than by the table itself (the built-in admin policy can still edit it, G-16).

7 · GitHub events keep cards in step

The requirements say webhooks “update work_item”. We land them in a dedicated append-only repo_event table first, then a block applies them. That keeps the raw delivery for debugging, makes replays idempotent, and lets one event touch several tables (item, CI strip, activity, audit).

8 · Streaming and live status

nostackai offers a WebSocket gateway, not SSE. Cards, pills and the activity feed update through it. The agent session panel is the one place the design cannot be matched exactly; see G-01.

9 · Metrics pipeline

Burndown, velocity and cumulative flow need history that the live tables do not keep. We record it from day one: every lane change writes a lane_transition row, and a nightly schedule writes a flow_snapshot with per-lane counts. A Glyph turns those into series for any from/to.
