P3 started (2026-10-30): 3 of about 55 blocks. pd_req_submit_request, pd_req_vote_request and pd_req_list_requests are created and dry-run tested. Reads are real in a dry run; writes are stubs, so item ids, the project code and the submitter email show empty there. A real write test needs a signed-in user and the org's client id and API key from the console.
  • How a block is written: inputSchema declares the body fields; a branch of steps runs only when a condition lists it; an end step sets the response (output: "{{step}}"). The caller is {{context.userId}} and {{context.email}}; flags arrive as {{params.flags.key}} and were already evaluated correctly in the dry run.
  • Errors: there is no step that returns an HTTP error status. A refused request returns {"error":"title_too_short"} with a success status, so the front end's API layer must treat a body with error as a typed error (G-26).
  • Limits: 20 steps and 500 list items per block, so the larger blocks (pd_dev_get_item, backlog list) must be split or use a Glyph.
  • Not yet applied: pd_req_list_requests accepts project_id but does not filter by it yet; the project and group scoping comes with the member and project blocks.
  • Maybe fixable: the platform's entity format does list an excludeOps setting, which the create tool rejects. import_metadata may accept it, which would make the audit tables truly append-only. To try before P4.
