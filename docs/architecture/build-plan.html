Build plan

Order of work through MCP

Nothing below has been run. Every step is an MCP call against org paired-egih; no nostackai source is touched. The order follows the platform's own rule: entities first, then logic, then pointing the app at the app API.

P0 · Decisions and preconditions

  • Answer the eight items on the Gaps page.
  • Confirm in the console: org tenancy is multi, plan tier, front-end domain.
  • Spike (10 minutes): create a throw-away entity with an autoincrement and a formula column, one Logic Block, and read list_tenant_acl_policies. Settles G-11 and G-22 before anything depends on them. Delete the spike afterwards.
  • Adopt connectors with setup_connector: github (named github, personal), github (named automation, shared), muse-code (main), slack (notify), email, s3. Then describe_connector each to confirm exact action fields (merge SHA, create_branch ref).

P1 · Entities and flags

  1. create_entity in dependency order: member → project → project_group → project_group_member → sprint → delivery → work_item → work_item_worker / vote / dependency → checklist_item → activity_entry → audit_event → lane_transition → flow_snapshot → repo_event → plan → agent_session → session_step → session_gate → hook → project_skill → preflight_run → retro_digest → permission_cell → notification_pref → invite.
  2. Pass a description on every entity (stored as its summary; it flows into the Architecture Studio and OpenAPI).
  3. create_feature_flag for the twelve keys on the integrations page (trim to ten on a Free plan).

Check: list_entities shows 27 new entries plus the 7 platform ones; each lookup target exists; no entity has more than 5 lookups.

P2 · Access and bootstrap

  1. create_tenant_acl_policy: pd-requester, pd-dev, pd-owner, pd-admin, pd-agent. Deny direct create/update/delete on governed entities by simply not granting them.
  2. set_default_member_access → pd-requester (the least-privileged policy a new user needs: submit and vote). I will state this choice when done; admins raise anyone with assign_user_acl.
  3. create_glyph + publish_glyph pd_bootstrap_tenant; run with invoke_glyph for tenant 2vrdf.
  4. assign_user_acl: the existing admin user gets pd-owner in addition to adminacl.

Check: list_tenant_acl_policies; invoke_glyph output lists permission cells created.

P3 · Portal and board

  1. Create blocks: submit_request, vote_request, list_requests, list_items, get_item, move_item, set_owner, set_workers, advance_item, signoff_checklist, get_checklist, send_prompt, bulk_items, add/remove_dependency, get_audit.
  2. Create run_triage, which needs a tenant AI provider.
  3. Seed with pd_seed_demo through invoke_glyph (dev only).

Check: test_logicblock for each happy path and each rejection (agent sign-off → 403, gate closed → 409, duplicate vote → toggle). Writes are real, so test on tenant 2vrdf only.

P4 · GitHub and webhooks

  1. set_connector_webhook_landing for the five GitHub events into repo_event (insert).
  2. create_event on repo_event after create → custom_api pd_sys_apply_repo_event.
  3. Create git_op, submit_review, merge_pr, get_deployments.
  4. Hand the tenant admin the checklist from Integrations §5. Then get_connector_webhook_info for the URL.

Check: invoke_connector_action get_repository on a test repo; push to a test branch; list_connector_logs shows a 2xx delivery; list_event_deliveries shows the block ran; the card's pill changed.

P5 · Plan and agent session

  1. Crews pd-planner, pd-checklist-reviewer, pd-preflight (created as drafts, then update_crew to staged → active). Their repo access is connector.invoke tools, one per GitHub action (get_file_contents, compare_branch, list_pull_request_files), pointed at github for person-started runs and github:automation for webhook-started runs. No repo Glyph is needed (G-10).
  2. Blocks: request_plan, revise_plan, approve_plan, session_gate_decision, resume_session, rebase_item, post_step, escalate_item, record_precheck, comment_review, sync_session.
  3. One-time repo setup via the connector's setup_workflow, setup_permissions, setup_secret (needs a repo-admin token from the tenant).
  4. Schedules sync-sessions and flow-snapshot (paid plan).

Check: request a plan on a seeded card, approve it, see a branch appear, a runner start, a PR open, a checklist pre-check land, and a human sign-off advance the card. Confirm that calling signoff as the agent identity returns 403.

P6 · Planning and analytics

  1. Blocks: create_sprint, close_sprint, create_delivery, update_delivery_items, run_release_preflight, run_delivery_preflight, promote_release, get_metrics, prepare_retro; Glyph pd_metrics; crew pd-preflight.
  2. Events for blocked items, plan ready, session paused, invite sent.

Check: invoke_glyph pd_metrics across 7/14/30/90-day ranges gives consistent slices; the seeded two-branch overlap on queue/retry.ts is flagged by pre-flight.

P7 · Agent configuration and providers

Blocks: get/put_claude_md, list/put/delete_skill, list/update_hooks, update_tenant_hooks, Glyph pd_render_hooks, list_providers, update_project_settings, invite_member, manage_invite, update_permissions.

Check: committing CLAUDE.md creates a commit on the default branch and updates the stored sha; editing the file in GitHub then syncing shows drift.

P8 · Readiness, descriptions, export

  1. get_tenant_readiness for each tenant; give the tenant admin the remaining steps.
  2. get_asset_descriptions; fill any gap with set_asset_description so the Architecture Studio and OpenAPI explain every asset.
  3. export_metadata to keep a copy of all definitions in the repo (backend/export/) for review and recovery.
  4. Set Allowed Domains and App URL once the domain exists.
  5. Production: console deploy (publish → activate), later.
